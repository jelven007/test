# 一进二策略研究系统需求规格

## 1. 文档信息

- 版本：`1.0`
- 状态：迭代前基线
- 适用范围：沪深主板首板晋级二板研究、次日计划和盘中监控
- 行情来源：`mootdx`
- 时区：`Asia/Shanghai`

## 2. 产品目标

系统在每个交易日收盘后生成下一交易日的条件观察计划，并在交易日盘中持续采集候选股票
行情，结合开盘、价格、板块强度、时间窗口和不可逆放弃条件，给出可解释的实时研究建议。

系统必须解决：

1. 行情、策略输入、计算结果、状态变化和报告均有持久化落点。
2. 行情采集、实时计算、策略决策、查询展示相互解耦。
3. 任一服务重启后可以恢复状态、重放数据并解释历史判断。
4. 数据过期、缺失或来源异常时停止生成入场确认。
5. 全链路不包含自动下单和券商账户操作。

## 3. 用户与场景

### 3.1 研究用户

- 查看每日市场环境、候选评分和入选依据。
- 查看每只股票的竞价区间、入场条件、放弃条件和退出计划。
- 盘中查看最新行情、数据时效、策略状态和状态变化原因。
- 查询历史计划、历史判断和报告文件。

### 3.2 系统运维人员

- 查看采集延迟、Kafka 积压、Flink Checkpoint、存储健康和 API 状态。
- 对失败消息执行重放或转入死信处理。
- 执行备份恢复、版本回滚和数据一致性校验。

## 4. 业务范围

### 4.1 包含

- 沪深主板 10cm 股票。
- 首板股票池、炸板池、连板高度和题材活跃度。
- 每个工作日 `16:20` 生成下一交易日计划。
- 动态候选池的盘中盘口快照和一分钟线监控。
- 研究建议状态：等待、观察、确认待核验、放弃、不追、行情异常。
- Markdown、JSON、CSV 报告和 Web 看板。

### 4.2 不包含

- 自动下单、账户登录、持仓同步和资金管理。
- Level-2、完整逐笔成交或逐笔委托能力承诺。
- 对收益率、成交概率或涨停排队结果作保证。
- 将公开人物的交易系统视为可精确复制的事实。

## 5. 硬性业务规则

| 编号 | 规则 |
| --- | --- |
| BR-001 | 行情数据单一来源为 `mootdx`，不得引入 AkShare 等并行行情源 |
| BR-002 | 策略范围聚焦首板晋级二板，默认排除 ST、退市、创业板、科创板和北交所 |
| BR-003 | 候选股票前一交易日成交额不得低于 2 亿元 |
| BR-004 | 盘中实时入场研究窗口最晚为 `10:00:00`，之后不得恢复为可入场状态 |
| BR-005 | 当日最低价跌破昨日收盘价后，当前计划永久进入放弃状态 |
| BR-006 | 开盘涨幅不在策略合格区间时不得给出入场确认 |
| BR-007 | 开盘涨幅低于放弃下限或高于放弃上限时进入不可逆放弃状态 |
| BR-008 | 个股封板不能单独证明主线成立，必须结合题材上涨家数和前排助攻 |
| BR-009 | 交易时段盘口目标采集周期为 1 秒，一分钟线目标刷新周期为 60 秒 |
| BR-010 | 非交易时段采集周期降为 60 秒 |
| BR-011 | 行情时间不可核验、数据过期、昨收不一致或采集失败时暂停判断 |
| BR-012 | 候选仅供研究参考，任何输出都不得成为无条件买入或自动下单指令 |

| FR-DATA-001 | 复用 mootdx 长连接，批量采集动态监控股票盘口快照 | P0 |
| FR-DATA-002 | 每 60 秒刷新当日一分钟线，并按股票和分钟幂等保存 | P0 |
| FR-DATA-003 | 行情节点失败时自动切换备用节点并记录切换事件 | P0 |
| FR-DATA-004 | 采集器写入 RocksDB WAL 后发布 Kafka，恢复后补发未确认事件 | P0 |

## 7. 非功能需求

| 编号 | 指标 |
| --- | --- |
| NFR-001 | 正常交易时段，盘口采集成功事件端到端可见延迟 P95 小于 3 秒 |
| NFR-002 | 监控查询 API 在缓存命中时 P95 小于 200ms，历史查询 P95 小于 1 秒 |
| NFR-003 | 单 Pod 或单节点故障时，已确认事件 RPO 为 0，服务 RTO 小于 60 秒 |
| NFR-004 | 区域级故障目标 RPO 不超过 5 分钟，RTO 不超过 30 分钟 |
| NFR-005 | Kafka 到权威存储采用至少一次投递和幂等消费 |
| NFR-006 | 所有持久化数据静态加密，服务间通信使用 TLS |
| NFR-007 | 数据库和消息系统不得直接暴露公网 |
| NFR-008 | 核心业务规则分支必须具备自动化测试，整体行覆盖率目标不低于 85% |
| NFR-009 | 目标首期支持不超过 200 只动态监控股票；扩容前必须重新压测 |
| NFR-010 | Redis 清空后，实时投影可从 Kafka 或权威存储恢复 |

## 8. 数据持久化要求

“全量持久化”指进入系统并被确认接收的行情、指标、决策、配置、运行结果和报告都有
可恢复的持久化落点，不代表所有副本永久保留。

- 原始行情：Kafka 短期重放，ClickHouse 热查询，S3/MinIO 长期归档。
- 策略状态：PostgreSQL 权威保存。
- 最新快照：Redis 加速，可重建。
- 报告文件：S3/MinIO 版本化保存。
- 日志、指标和追踪：独立可观测存储并配置生命周期。

具体生命周期见 [数据与存储](03-data-storage.md)。

## 9. 验收场景

| 编号 | 场景 | 期望结果 |
| --- | --- | --- |
| AC-001 | 候选盘中最低价跌破昨收后反弹涨停 | 状态保持“放弃”，重启后不恢复 |
| AC-002 | 09:59:59 满足条件，10:00:00 后再收到重复事件 | 不产生新的入场确认 |
| AC-003 | Kafka 重复投递同一行情事件 | ClickHouse、状态机和审计无业务重复 |
| AC-004 | Redis 数据全部清空 | 可自动重建，权威状态不丢失 |
| AC-005 | mootdx 当前节点失败 | 自动切换节点，页面显示短暂降级和恢复时间 |
| AC-006 | 行情超过时效阈值 | 页面保留最后报价但暂停策略判断 |
| AC-007 | 服务在状态迁移后、提交 offset 前崩溃 | 重启重放后不产生重复迁移 |
| AC-008 | 16:20 任务被调度两次 | 仅一个策略运行成功，另一个幂等退出 |
| AC-009 | Kafka 数据已过保留期 | 可从 S3/MinIO 原始归档回放 |
| AC-010 | 报告生成成功 | Markdown、JSON、CSV 内容与数据库元数据一致 |

## 10. 发布限制

以下条件任一不满足时，不得将生产版本标记为可用：

- 关键业务验收场景未自动化。
- PostgreSQL、ClickHouse 或对象存储没有备份恢复验证。
- 行情延迟和 Kafka 积压没有告警。
- API 或事件 Schema 存在未兼容变更。
- 页面无法明确区分实时数据、延迟数据和失效数据。
