# 测试与质量策略

## 1. 质量目标

测试体系必须证明：

- 核心策略规则正确且时间边界明确。
- 重复、乱序、延迟和缺失数据不会产生错误入场确认。
- 服务重启、消息重放和缓存丢失不会改变权威业务结果。
- API 和 Kafka Schema 与文档契约一致。
- 备份、恢复和降级路径可以实际执行。

## 2. CURRENT 测试基线

当前仓库使用 Python `unittest`，覆盖：

- 涨停价计算、首板池、炸板池和连板高度。
- 候选过滤、评分、行业限额和报告一致性。
- 竞价、开盘、跌破昨收、封板快照、可配置截止时间（默认 10:00）和行情过期。
- mootdx 长连接复用、分钟线刷新和节点切换。
- HTTP 查询不重复触发行情采集。
- 补充清单校验和报告选择。
- PostgreSQL SQL 参数与重复 Inbox 短路。
- ClickHouse 列映射和分钟线进程内去重。
- Redis 投影 TTL、MinIO 内容哈希和对象键校验。
- 日报及盘中双写的部分失败可见性。
- Kafka/WAL 可靠发布、真实 Topic 坐标幂等和 Outbox 重试。
- 调度器启动补跑、持久化完成标记和刷新任务完整事务。
- 策略配置校验、不可变策略、父子血缘、唯一激活和软删除。
- 每策略每日记录、历史回填幂等和跨策略隔离。
- 月度研究、严格可买执行分析和盈利约束优化。
- 四页共享 UI 结构、组件、表格和移动端防溢出规则。

截至 `2026-09-25`，快速测试基线为 **158 项通过、8 项跳过**。跳过项主要是未配置
真实 PostgreSQL/Compose 时的集成检查；启用相应环境后必须单独执行。

当前测试命令：

```bash
PYTHONPATH=src python3 -m unittest discover -s tests -v
```

这些测试必须保留，并逐步迁移为生产组件的领域层回归测试。
适配器单元测试使用注入客户端验证协议和参数；真实组件双写测试需先启动 Compose，再执行：

```bash
make infra-check
make integration-test
```

## 4. 单元测试

### 4.1 策略状态机

每个测试使用固定时钟、固定策略版本和显式输入事件。必须覆盖：

- 盘前、竞价、等待开盘、早盘、午休、午盘、收盘和周末。
- 开盘涨幅边界值及小数舍入。
- 跌破昨收后反弹和涨停。
- 09:59:59 与 10:00:00 边界。
- 昨收不一致、行情无效、源时间未来和数据过期。
- 静态不合格股票即使封板也不恢复。
- 已进入不可逆状态后收到旧事件或乱序事件。
- 同一输入事件重复处理。
- 策略版本变化不回写历史计划。
    - 不同 `entry_cutoff_time` 的截止边界，包括研究候选 `09:45`。

核心状态迁移分支要求 100% 覆盖。

### 4.2 事件和数据转换

- 股票代码保持字符串。
- 时间保留毫秒和时区。
- 金额、成交量和价格单位一致。
- `event_id` 对同一规范化事件稳定，对关键字段变化敏感。
- 分钟线重复修订只保留最新版本。
- 无效 NaN、Infinity 和负值被拒绝或明确标记。

## 5. 契约测试

### 5.1 HTTP

- `docs/openapi.yaml` 必须通过 OpenAPI 校验。
- 服务响应必须通过 Schema 校验。
- 错误结构、状态码、分页和时间格式必须一致。
- 兼容接口 `/api/*` 和目标接口 `/api/v1/*` 在迁移期进行语义对照。

### 5.2 Kafka

- `docs/asyncapi.yaml` 必须通过 AsyncAPI 校验。
- 生产者和消费者共享 Schema，不复制手写字段定义。
- 同一 Topic 主版本只允许增加可选字段。
- 破坏性修改必须创建新主版本 Topic。
- DLQ 必须保留原 Topic、partition、offset 和错误详情。
- 计划、决策和报告事件必须携带可定位策略版本的标识。

## 6. 组件测试

使用 Testcontainers 或等价的临时环境启动真实依赖：

### PostgreSQL

- 迁移可以从空库完整执行。
- 唯一键阻止重复日报和重复 Inbox。
- 状态、事件和 Outbox 原子提交。
- 乐观锁冲突可重试且不会覆盖新状态。

### Kafka

- 按股票键进入固定分区。
- 生产者幂等和 `acks=all` 配置生效。
- 消费者在落库失败时不提交 offset。
- 重试耗尽后进入 DLQ。

### ClickHouse

- 重复盘口事件最终只形成一个逻辑结果。
- 分钟线修订可被最新版本查询。
- 分区裁剪和指定查询满足响应时间要求。
- TTL 和对象存储归档策略生效。

### Redis

- 最新快照更新保持时间单调。
- 旧事件不能覆盖新投影。
- TTL 正确。
- 清空后重建结果与 PostgreSQL、ClickHouse 一致。

### S3/MinIO

- Parquet 和报告写入后内容哈希一致。
- 重复任务不会生成冲突对象。
- Manifest 能定位完整输入和产物。

### Flink

- 窗口边界、Watermark 和迟到数据策略正确。
- Checkpoint 恢复后不丢失已确认状态。
- 从 Savepoint 升级时 Schema 兼容。
- 乱序输入不会导致板块指标时间倒退。

## 7. 集成测试场景

| 编号 | 场景 | 验证点 |
| --- | --- | --- |
| IT-001 | 行情事件进入 Kafka | ClickHouse、Flink 和归档器均收到同一 `event_id` |
| IT-002 | Flink 生成窗口指标 | 指标写入 ClickHouse 和 Redis |
| IT-003 | 状态机处理有效行情 | PostgreSQL 状态、事件、Outbox 一致 |
| IT-004 | 消费者提交前崩溃 | 重放后不产生重复决策 |
| IT-005 | 乱序行情到达 | 不可逆状态不回退 |
| IT-006 | Redis 清空 | 投影重建且 API 结果恢复 |
| IT-007 | Kafka 短暂不可用 | WAL 保存并在恢复后补发 |
| IT-008 | Flink 停止 | 原始行情继续持久化，策略依赖指标时降级 |
| IT-009 | PostgreSQL 停止 | 不生成只存在 Redis 的新决策 |
| IT-010 | 同一日报时点重复触发 | 文件和数据库保持幂等，不产生重复业务记录 |
| IT-011 | 23:30 更新同一交易日报告 | 历史查询返回最新生成时间和更新后的内容 |
| IT-012 | 周末或节假日触发日报任务 | 正常跳过且不生成前一交易日的重复报告 |

## 8. 端到端测试

### 8.1 日报流程

1. 准备固定交易日的 mootdx 录制数据。
2. 触发日报任务。
3. 验证 PostgreSQL 运行、候选和计划。
4. 验证对象存储 Markdown、JSON、CSV 和 Manifest。
5. 验证 API 与报告内容一致。
6. 再次触发同一任务，验证幂等。

### 8.2 盘中流程

1. 加载当日计划。
2. 回放竞价、开盘、跌破昨收、封板和 10:00 后行情。
3. 验证每个状态迁移及解释文本。
4. 在不可逆状态后重启策略服务。
5. 继续回放反弹行情，验证状态不恢复。
6. 验证 Web 展示源时间、采集时间和失效状态。

### 8.3 数据异常

- 源时间缺失。
- 昨收发生变化。
- 分钟线停滞。
- 盘口价格为零。
- 单股票缺失但批次其他股票正常。
- 所有 mootdx 节点不可用。

所有异常都必须停止该股票的入场确认。

### 8.4 多策略与历史记录

1. 创建策略副本并校验父策略、revision 和参数差异。
2. 验证数据库阻止原地修改名称、配置和血缘。
3. 连续激活不同策略，确认最终仅一条激活。
4. 同一行情驱动多份计划，按 `plan_id + source_event_id` 分别幂等。
5. 重复回填一年交易日，确认只补空值、不覆盖已有数据。
6. 刷新任务排队后切换激活策略，确认 Worker 使用开始执行时的策略。

### 8.5 研究与收益

- 月度实验严格按时间划分训练、验证、留出，选参发生在留出评估前。
- 区分触及涨停、收盘封板和严格可买。
- 严格可买必须同时满足竞价、昨收、截止时间、有量开板和回封条件。
- T+1 收益使用下一交易日，不跨错节假日。
- 往返成本按 bp 正确扣除，不可卖代理的净收益保持 `null`。
- 盈利约束不通过时不得持久化候选；通过时创建未激活子策略。

### 8.6 Web

- 四页加载同一版本 `ui-standard.css`，主导航顺序一致。
- 按钮、输入框、状态标签、分段控件和表格类名满足共享规范。
- 刷新按钮触发异步任务、运行中禁用、成功后重载。
- 桌面端与 `390x844` 视口无页面级横向溢出、文字遮挡和不可点击控件。
- 浏览器检查与静态 DOM/CSS 测试都通过后才视为完成。

## 9. 性能测试

首期容量模型：

- 动态监控股票不超过 200 只。
- 每只股票目标每秒一个盘口采样。
- 一分钟线每 60 秒刷新。
- 正常交易日约 4 小时连续竞价。

目标：

| 指标 | 目标 |
| --- | --- |
| 采集成功事件端到端可见延迟 | P95 < 3 秒 |
| Kafka Consumer Lag | 正常持续低于 5 秒 |
| 最新监控 API | 缓存命中 P95 < 200ms |
| 历史报告 API | P95 < 1 秒 |
| SSE 同时连接 | 首期 200 |
| 单服务 CPU | 稳态低于 70% |
| 单服务内存 | 稳态低于容器限制 75% |

压测必须包含：

- 正常稳态。
- 开盘突发流量。
- Kafka 重放。
- Redis 缓存击穿。
- ClickHouse 大时间范围查询。
- API 多副本滚动发布。

## 10. 故障与恢复测试

- 终止采集 Leader，验证备用实例 60 秒内接管。
- 终止 Kafka Broker，验证 ISR 和生产者重试。
- 终止 Flink TaskManager，验证 Checkpoint 恢复。
- 在数据库提交后、offset 提交前终止策略实例。
- 删除 Redis 数据并执行投影重建。
- 从 PostgreSQL 时间点备份恢复到隔离环境。
- 从对象存储恢复 ClickHouse 指定分区。
- 验证报告对象版本和内容哈希。

## 11. 数据对账

每日收盘后自动生成：

- 采集器发布事件数。
- Kafka 各分区消息数和最大 offset。
- ClickHouse 去重前后记录数。
- S3 Parquet 记录数和文件哈希。
- 状态迁移数和不可逆终态数。
- 报告候选数和 PostgreSQL 候选数。

差异超过阈值时阻止当日报告标记为“完整”。

## 12. 发布门槛

生产发布必须满足：

- 单元测试、Schema 测试和组件测试全部通过。
- 核心状态机分支覆盖率 100%，整体行覆盖率不低于 85%。
- 无 P0/P1 缺陷。
- 性能指标达到目标且无持续资源泄漏。
- 数据重放和 Redis 重建通过。
- 数据库迁移具备前滚和回滚方案。
- 备份恢复在最近一个发布周期内验证成功。
- 看板明确显示数据新鲜度和降级状态。
- 策略目录的不可变和唯一激活约束通过数据库级测试。
- 研究结果明确样本量、成本和成交代理，不将历史结果描述为收益保证。
- 四个页面通过桌面和移动端视觉回归。
